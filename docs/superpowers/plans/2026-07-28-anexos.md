# Anexos visíveis e baixáveis — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mostrar, na mensagem selecionada no painel de leitura, a lista de anexos reais (nome, tipo, tamanho) — distintos de imagens `cid:` já resolvidas inline no corpo — e permitir baixar cada um pro disco, um por vez.

**Architecture:** `MessageRenderer` (já usa MimeKit pra montar o HTML) passa a também extrair metadado leve de `MimeMessage.Attachments` pra dentro de `RenderedMessage.Attachments`. Salvar um anexo relê a mensagem do zero a partir do `.dbx` de origem (mesma `MessageRef`) e decodifica só o anexo pedido — nunca mantém nenhum parser MimeKit "vivo" entre a abertura da mensagem e um clique em "Salvar" que pode vir minutos depois. A UI reaproveita o padrão de barra já usado duas vezes nesta janela (`ImagesBlockedBar`, `RecoverableBar`), mas totalmente data-bound (sem toggling manual em code-behind), já que `MessageReader.Current` é `[ObservableProperty]`.

**Tech Stack:** .NET 9, C#, WPF, MimeKit 4.17.0 (já referenciado em `LEC.App`), xUnit. Nenhuma dependência nova.

## Global Constraints

- Nenhuma mudança em `LEC.MailStore` ou `LEC.DbxFormat` — tudo fica em `LEC.App`, mesma camada que já faz o parse MIME hoje.
- Só download individual — sem "salvar todos" (decisão explícita do usuário, 2026-07-28).
- Sem preview/thumbnail de conteúdo do anexo — só nome + tamanho + botão "Salvar".
- `AttachmentInfo.Index` é só um identificador posicional válido dentro de uma única leitura de `message.Attachments` — nunca persistido, nunca comparado entre releituras diferentes além de "mesma mensagem, mesmo `.dbx` imutável" (o que sempre vale, já que arquivos de origem são somente-leitura).
- Anexo sem nome de arquivo no MIME usa um nome de fallback determinístico (`anexo-{n}`), nunca fica vazio.
- Continua tudo somente-leitura quanto ao `.dbx`/`.pst` de origem — a única escrita é o arquivo de destino que o usuário escolhe ao salvar.
- Sem automação de teste de UI/XAML — mesmo padrão de toda fase anterior deste projeto (verificação manual apenas).

    // MimeMessage.Attachments já separa anexo de verdade de parte inline referenciada por
    // cid: (essas ficam só no corpo HTML, via ResolveCidImages/BuildContentIdIndex acima) --
    // verificado contra mensagens reais do BCP/ na Task 5 deste plano.
    private static IReadOnlyList<AttachmentInfo> ExtractAttachments(MimeMessage message)
    {
        var attachments = new List<AttachmentInfo>();
        int index = 0;

        foreach (var entity in message.Attachments)
        {
            if (entity is not MimePart part)
            {
                continue;
            }

            string fileName = string.IsNullOrEmpty(part.FileName) ? $"anexo-{index + 1}" : part.FileName;

            using var counting = new MemoryStream();
            part.Content?.DecodeTo(counting);

            attachments.Add(new AttachmentInfo(fileName, part.ContentType.MimeType, counting.Length, index));
            index++;
        }

        return attachments;
    }
```

    /// <summary>
    /// Relê e reparseia a mensagem inteira do zero e escreve só os bytes decodificados do
    /// anexo pedido no disco. Deliberadamente não compartilha nada com RenderAsync/
    /// ExtractAttachments -- o painel de leitura pode estar mostrando uma mensagem por
    /// minutos antes do usuário decidir salvar um anexo, e reparsear a cada vez evita manter
    /// qualquer parser ou stream do MimeKit "vivo" por esse tempo todo.
    /// </summary>
    public static async Task SaveAttachmentAsync(Stream rawMessage, int attachmentIndex, string destinationPath, CancellationToken ct = default)
    {
        var message = await MimeMessage.LoadAsync(rawMessage, ct);
        var attachments = message.Attachments.OfType<MimePart>().ToList();

        if (attachmentIndex < 0 || attachmentIndex >= attachments.Count)
        {
            throw new InvalidOperationException($"Anexo não encontrado nesta mensagem (índice {attachmentIndex}).");
        }

        if (attachments[attachmentIndex].Content is not { } content)
        {
            throw new InvalidOperationException("Este anexo não tem conteúdo para salvar.");
        }

        using var destination = File.Create(destinationPath);
        content.DecodeTo(destination);
    }
```

    private async void SaveAttachment_Click(object sender, RoutedEventArgs e)
    {
        if ((sender as FrameworkElement)?.Tag is not AttachmentInfo attachment || _viewModel.MessageReader is null)
            return;

        var dialog = new SaveFileDialog { FileName = attachment.FileName };
        if (dialog.ShowDialog() != true)
            return;

        try
        {
            await _viewModel.MessageReader.SaveAttachmentAsync(attachment.Index, dialog.FileName);
            _viewModel.StatusText = $"Anexo salvo em {dialog.FileName}";
        }
        catch (Exception ex)
        {
            _viewModel.StatusText = $"Não foi possível salvar o anexo: {ex.Message}";
        }
    }
